# RCA — caricature-saas redeploy failed (run ada5e129-f519-4b0b-8360-f0e87db71161)

## Symptom
Deploy pipeline failed at the `deploy` (deploy_k8s) step. Pod
`r-ada5e129-...-hzq8j` went `CrashLoopBackOff (early)`, restarts=3, lastExit=1/Error.
Backend dies on boot → `Backend died, shutting down nginx...` → nginx then refuses
`/health` (connection refused on 127.0.0.1:8001) and the rollout never becomes ready.

## Root cause (source + existing prod index conflict)
On FastAPI startup, `server.py:171 startup()` runs `ensure_gift_indexes()` in
`backend/routers/gifts.py:915`, which calls:

```python
await db.gift_codes.create_index("session_id", unique=True, sparse=True)
```

The production database `caricature-saas-test_database` already contains an index
named `session_id_1` with spec `{ session_id: 1, unique: true }` — **without** the
`sparse` flag (verified via list_indexes on gift_codes). MongoDB refuses to (re)create
an index with the same auto-generated name but a different spec:

```
pymongo.errors.OperationFailure: An existing index has the same name as the requested index...
Requested index: { v: 2, unique: true, key: { session_id: 1 }, name: "session_id_1", sparse: true }
existing index:  { v: 2, unique: true, key: { session_id: 1 }, name: "session_id_1" }
code: 86, codeName: IndexKeySpecsConflict
```

The exception is unhandled in the startup lifespan, so application startup fails and
the container exits — the CrashLoopBackOff. This is why it works in a fresh preview DB
(no pre-existing index) but fails against the existing production collection.

### Evidence
- fetch_app_logs (run ada5e129...): repeated `OperationFailure ... IndexKeySpecsConflict (code 86)` on `session_id_1`, followed by `Application startup failed. Exiting.` and `Backend died, shutting down nginx...`.
- mongo_query list_indexes on `gift_codes` (prod db caricature-saas-test_database): existing `session_id_1` = `{session_id:1, unique:true}` (NO sparse), while the other indexes (`code_1`, `code_hash_1`, `order_id_1`) ARE sparse+unique. So only `session_id_1` conflicts with the new sparse spec.

## Fix (needs a source change by E1 — not a manifest/infra issue)
Make `ensure_gift_indexes()` tolerant of a pre-existing index with a different spec.
Recommended options (pick one):

1. **Drop-then-recreate with the new spec** (handles the migration cleanly):
   ```python
   try:
       await db.gift_codes.create_index("session_id", unique=True, sparse=True)
   except OperationFailure as e:
       if e.code == 86:  # IndexKeySpecsConflict
           await db.gift_codes.drop_index("session_id_1")
           await db.gift_codes.create_index("session_id", unique=True, sparse=True)
       else:
           raise
   ```
2. **Use a distinct explicit index name** for the new sparse index and drop the old one.
3. If startup must never be blocked by index management, wrap `ensure_gift_indexes()`
   so index-creation failures are logged (warning) rather than crashing the lifespan.

Alternatively (one-time ops action), an admin can drop the old index in MongoDB Atlas
(`db.gift_codes.dropIndex("session_id_1")`) so the next deploy recreates it as sparse —
but the code should still be made idempotent to prevent recurrence.

## Note
Not a manifest/platform failure. Resuming the pipeline unchanged will reproduce the
identical crash, so no resume was attempted.
