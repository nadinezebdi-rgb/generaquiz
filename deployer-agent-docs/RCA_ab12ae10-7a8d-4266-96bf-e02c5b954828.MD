# RCA — caricature-saas redeploy failure (run ab12ae10-7a8d-4266-96bf-e02c5b954828)

## Symptom
Deploy failed at the `deploy_k8s` step. Pod `r-ab12ae10-...-qd9vm` entered **CrashLoopBackOff (early), restarts=3, lastExit=1/Error**. nginx reported `Backend died, shutting down nginx...` and `/health` returned connection-refused (backend never bound to :8001).

## Root cause (CONFIRMED)
FastAPI startup crashes while building Mongo indexes. Stack trace terminates in:

```
await db.gift_codes.create_index("session_id", unique=True, sparse=True)
  File "/app/backend/routers/gifts.py", line 915, in ensure_gift_indexes
  File "/app/backend/server.py", line 171, in startup
pymongo.errors.OperationFailure: An existing index has the same name as the requested index.
Requested index: { v: 2, unique: true, key: { session_id: 1 }, name: "session_id_1", sparse: true }
existing index:  { v: 2, unique: true, key: { session_id: 1 }, name: "session_id_1" }
code: 86, codeName: IndexKeySpecsConflict
```

The new code wants `session_id` indexed as `unique + sparse`. The production DB already holds an index named `session_id_1` that is `unique` **but NOT sparse**. Mongo refuses to redefine an existing index name with different options (code 86). Because `ensure_gift_indexes()` runs inside the FastAPI lifespan `startup`, the exception aborts startup → `Application startup failed. Exiting.` → container exits 1 → CrashLoopBackOff → `deploy_k8s` times out waiting for readiness.

### Evidence
- `mongo_query list_indexes` on `gift_codes` (db `caricature-saas-test_database`) returns:
  - `session_id_1`: `{ key: {session_id:1}, unique:true }`  ← **no `sparse`**
  - `code_1`, `code_hash_1`, `order_id_1`: all `unique + sparse` (these match the code and do not conflict)
- The same crash is in BOTH failed runs (ada5e129 and ab12ae10) — deterministic, not transient.
- The last successful run (a27802a0, 2026-11-12) predates the addition of `sparse=True` to the `session_id` index definition.

## Who fixes it — Code (E1)
This is a source/schema-migration bug in `backend/routers/gifts.py::ensure_gift_indexes` (~line 915). `create_index` is not idempotent when the desired options differ from an existing index of the same name. Options:

1. **Preferred — make the index creation migration-safe.** Before creating, drop the old index if its spec differs, then recreate:
   ```python
   try:
       await db.gift_codes.create_index("session_id", unique=True, sparse=True)
   except OperationFailure as e:
       if e.code == 86:  # IndexKeySpecsConflict
           await db.gift_codes.drop_index("session_id_1")
           await db.gift_codes.create_index("session_id", unique=True, sparse=True)
       else:
           raise
   ```
   (Apply the same guard to any other index whose options were changed.)

2. **Alternative** — if `sparse` is not actually required for `session_id`, revert the definition back to `unique=True` only (matching what is already in the DB), so no conflict occurs.

3. **Resilience** — index provisioning at startup should not hard-crash the whole app; wrap `ensure_gift_indexes` so an index conflict logs and continues rather than killing the process.

After E1 applies the fix, redeploy. No manifest change is needed; no tier/secret/domain issue is involved.

## Not the cause
- Not a manifest/template problem (crash is app source during Mongo index build).
- Not a secrets problem — MONGO_URL is valid (the app connected and queried indexes successfully; the failure is purely the index spec conflict). The `SENDER_EMAIL` Resend line is a benign WARNING, not the crash.
- Not OOM/tier — exit code is 1 (application error), not 137.
