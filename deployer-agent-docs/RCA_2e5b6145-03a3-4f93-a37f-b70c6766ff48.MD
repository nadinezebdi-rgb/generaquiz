# RCA — run 2e5b6145-03a3-4f93-a37f-b70c6766ff48 (caricature-saas)

## Symptom
Redeploy fails at the `deploy` (k8s) step. Pod CrashLoopBackOff (early), restarts=3, lastExit=1/Error. Backend dies on startup, nginx then shuts down, readiness never passes.

## Root cause (proven)
The FastAPI startup handler crashes while ensuring Mongo indexes.

Stack trace (from rollout logs):
```
File "/app/backend/server.py", line 171, in startup -> await handler()
File "/app/backend/routers/gifts.py", line 915, in ensure_gift_indexes
    await db.gift_codes.create_index("session_id", unique=True, sparse=True)
pymongo.errors.OperationFailure: An existing index has the same name as the requested index...
Requested index: { unique: true, key: { session_id: 1 }, name: "session_id_1", sparse: true }
existing  index: { unique: true, key: { session_id: 1 }, name: "session_id_1" }
code: 86, codeName: IndexKeySpecsConflict
```

The code asks for an index named `session_id_1` WITH `sparse: true`, but the production DB already has an index of the same auto-generated name `session_id_1` WITHOUT `sparse`. MongoDB refuses to redefine an existing index's options under the same name → raises code 86, which propagates out of the lifespan startup and kills the process.

### Confirmed via live DB (mongo_query list_indexes on gift_codes, db caricature-saas-test_database):
```
_id_
session_id_1   { session_id: 1 }, unique: true            <-- NO sparse (the conflict)
code_1         { code: 1 },        unique: true, sparse: true
code_hash_1    { code_hash: 1 },   unique: true, sparse: true
order_id_1     { order_id: 1 },    unique: true, sparse: true
```
Note the sibling indexes (code_1, code_hash_1, order_id_1) are already sparse — only `session_id_1` predates the `sparse=True` change, so only it conflicts.

### History
Same crash on every recent redeploy: ada5e129 (Nov 16), ab12ae10 (Nov 16), 2e5b6145 (Nov 19). The last green runs (a27802a0, 5683c263 on Nov 12) predate the `sparse=True` addition. The live site still serves the Nov 12 image (active run a27802a0).

## Fix (code — E1)
`ensure_gift_indexes` must not blindly call `create_index(..., sparse=True)` on a name that already exists with different options. Options:
1. Make it idempotent/tolerant: catch `OperationFailure` code 86 and drop+recreate, e.g.
   ```python
   try:
       await db.gift_codes.create_index("session_id", unique=True, sparse=True)
   except OperationFailure as e:
       if e.code == 86:  # IndexKeySpecsConflict
           await db.gift_codes.drop_index("session_id_1")
           await db.gift_codes.create_index("session_id", unique=True, sparse=True)
       else:
           raise
   ```
2. Or give the new spec a distinct explicit `name=` and drop the old one.
3. Simplest if sparse isn't actually required: revert to `create_index("session_id", unique=True)` to match the existing index.

A redeploy after this code change will clear the crash.

## Alternative (user / DB action — unblocks without a code change)
Drop the stale index in MongoDB Atlas, then redeploy so the startup handler recreates it with sparse:
```
db.gift_codes.dropIndex("session_id_1")
```
(Safe: unique+sparse is a superset constraint; drop first, startup recreates it.)

## Not the cause
Not a manifest/template issue, not a tier/OOM issue (exit 1, not 137), not a missing secret. The Resend SENDER_EMAIL warning in the log is benign (a warning, not the fatal error).
